## What SETU is

Post-discharge patient monitoring for rural India — a hackathon project (started 2026-09-03). Patients get automated phone check-ins; AI extracts symptoms from speech, a **deterministic rule engine** (not the AI) decides risk level (normal/warning/critical), and critical cases alert an ASHA worker (village health worker) and the hospital. Core principle: **"AI extracts. Rules decide. Humans act."** — the LLM never makes the risk decision, only converts speech/text into structured data.

Three user roles, strictly separated at the backend query level (not just UI):
- **Patient** — receives calls, has a simple mobile-web app (check-in, reminders, AI chat, profile)
- **ASHA worker** — sees only their assigned patients, field app with map
- **Hospital/Admin** — sees all patients in their hospital, dashboards, analytics, reports

Stack: FastAPI (Python) + PostgreSQL backend, React + Vite + TypeScript + Tailwind frontend. Full architecture/rules/philosophy is in `SETU_PROJECT_CONTEXT.md` on the user's Downloads (not in this repo) — treat it as background, not gospel; a lot has changed since.

**IMPORTANT gotcha, confirmed again this session:** the backend process keeps dying/getting orphaned in this environment. `taskkill //F //PID <pid>` on the PID `netstat` reports as LISTENING often reports "SUCCESS" while the port keeps serving stale code — the process is invisible to PowerShell's `Get-Process` (different PID namespace/visibility in this sandbox). **Reliable fix:** use PowerShell, not taskkill: `Get-CimInstance Win32_Process -Filter "name='python.exe'"` to see real command lines and PIDs, then `Stop-Process -Id <id1>,<id2>,... -Force`. Kill *every* python.exe shown (there's usually the reloader parent + a multiprocessing-spawn child), then confirm with `curl http://127.0.0.1:8000/health` failing before restarting. Uvicorn's `--reload` also silently fails to pick up edits sometimes (StatReload logs "Reloading..." but never logs a new "Application startup complete" or "Started server process" line after) — if a code change doesn't seem to take effect, don't trust `--reload`, do the full kill-and-restart dance above.

## Prescription scan/upload/analyze feature — completed and verified live

User asked "a doc or patient can scan and upload a prescription image and that will be stored and analysed — what are we using here?" first as a question, then asked to build it. Investigated first: storage (local disk `uploads/` + Postgres `Document` row) and analysis (Gemini vision reading the image directly, no separate OCR — `prescriptions/providers/vision.py`) already existed and worked as two separate backend calls, but the **existing patient-facing UI was wired to two endpoints that don't exist** (`POST /api/v1/prescriptions/upload`, `GET /api/v1/prescriptions`) — so the feature looked built but the button just 404'd. Fixed the whole chain, found and fixed three more real bugs along the way:

1. **Document storage filename collision** (`backend/app/modules/documents/router.py`): uploads were saved as `uploads/{original_filename}` with no uniqueness — two different patients uploading a file both named e.g. "prescription.jpg" would silently overwrite each other on disk (the DB rows would stay separate with mismatched checksums pointing at the wrong bytes). Fixed to `uploads/{uuid4().hex}{ext}`; the original name is still preserved separately as `document_name`.

2. **`create_from_document` had no ownership check and blocked the patient role entirely** (`backend/app/modules/prescriptions/router.py`): the role check was `if user.role not in ("hospital", "admin", "asha")` — flatly rejecting patients trying to self-upload (contradicts "a doc **or patient** can scan and upload"), and for the roles it did allow, there was no check that the document actually belonged to a patient that user is authorized to see. Fixed: fetches the document first, runs `authorize_patient_access()` (same helper used everywhere else — a patient can only trigger this on their own document; hospital/asha need to actually own/be-assigned that patient), and now allows all four roles once ownership passes.

3. **`get_patient_prescriptions` crashed with `MissingGreenlet`** (`backend/app/modules/prescriptions/service.py`): accessed `p.medications` (a lazy SQLAlchemy relationship) without eager-loading, which isn't supported under async SQLAlchemy — would 500 the instant any prescription with medications existed (i.e. always, in practice). Fixed with `.options(selectinload(Prescription.medications))` on the query.

4. **`/patient/prescriptions` had no route and no nav entry at all** — the `Prescriptions.tsx` page file existed but `routes.tsx` never registered it and `PatientLayout.tsx`'s bottom nav had no link to it, so even a correctly-wired page would have been unreachable. Added the route and a 6th bottom-nav item ("Meds", Pill icon) to `PatientLayout.tsx`.

5. **Rewired `frontend/src/features/patient/pages/Prescriptions.tsx`** to the real two-step flow: `POST /api/v1/documents/upload` (multipart, gets back a `document.id`) → `POST /api/v1/prescriptions/from-document/{document.id}` (triggers Gemini extraction, gets back the created prescription) → refetch via `GET /api/v1/prescriptions/patient/{user.patient_id}` (was calling a bare `/api/v1/prescriptions` that doesn't exist).
